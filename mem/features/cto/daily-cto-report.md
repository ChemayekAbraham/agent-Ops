name: Daily CTO Report
description: Executive daily technology report emailed 00:00 EAT via get_cto_daily_report RPC + daily-cto-report edge function
type: feature
---
- RPC `get_cto_daily_report(p_date)` (SECURITY DEFINER, search_path public+extensions) aggregates platform, errors, auth, security, infra, backups, cron jobs, email and slow queries. Slow queries read `extensions.pg_stat_statements` inside an exception-safe block.
- Edge fn `daily-cto-report` renders a 14-section HTML executive report (KPI cards, bar charts, risk heat map, compliance table, weighted 0-100 technology health score) and sends via Mailgun.
- Cron job `daily-cto-report` runs `0 21 * * *` UTC = 00:00 EAT; defaults to the day just ended.
- Default recipient: joshwanda17@gmail.com. Override with POST body `{ "date": "YYYY-MM-DD", "recipients": [...] }`.
- Removed 2026-09-08, then rebuilt same day (`20260908150000` drop, `20260908160000` rebuild) with specific metric bugs fixed rather than carried forward:
  - **Rollback rate**: `get_cto_diagnostics`'s "Infrastructure Alerts" row computed `xact_rollback/xact_commit` straight from `pg_stat_database` — a lifetime ratio since the last stats reset (~148 days of uptime), not a same-day figure — and could show a "Breached" 14%+ alert on a day where the properly-delta'd `get_cto_daily_report` (via `db_stat_snapshots`) showed 0 rollbacks. Fixed to read the same day-over-day snapshot delta, gated by the same trustworthiness check the board-memo path already used (baseline must be exactly the prior day, counters must not have reset) — reports 'Unavailable' rather than a stale lifetime ratio when untrustworthy.
  - **Deadlocks**: the alert row claimed a "0 growth per day" threshold but only ever read the raw lifetime `pg_stat_database.deadlocks` counter (any deadlock ever recorded triggers "Watch" forever). `db_stat_snapshots` gained a `deadlocks` column so a real daily delta is now computed the same way as commits/rollbacks.
  - **Slow queries**: `pg_stat_statements` is lifetime-cumulative; `get_cto_issue_intelligence` classified these as 'Critical'/P1/"Today"/blocking-production despite the edge function's own rendering already labeling them "cumulative since the last statistics reset... no daily delta available" — a self-contradiction. Severity is now capped at Medium/P3, `blocking_production` is always false, and ETA reads "Ongoing — chronic performance debt" instead of claiming same-day urgency it can't support. A true per-query daily delta would need a `pg_stat_statements`-keyed snapshot table; not built in this pass (bigger, riskier change) — the lifetime figures are still surfaced for chronic-hotspot visibility, just not as false P1s.
  - **Sign-in latency**: `avg_login_ms_today` was a plain `AVG()`, so a single stalled/backgrounded session (one was ~18 minutes) skewed the whole day's reported latency. Now median-based (`percentile_cont(0.5)`) with sessions >=5 min excluded and counted separately as `login_stalled_sessions_today`; `login_ms_p95_today` added for the tail.
  - `get_cto_daily_addendum` needed no fix (already correctly scoped to the single day) — just recreated as-is since the removal migration dropped it too.
  - Daily health score (`scoreParts` in the edge function) was *not* corrupted by the rollback bug — it only reads client error rate for its Reliability pillar; only the weekly board-memo rollup's reliability pillar and the standalone "Infrastructure Alerts" section were affected.
- **2026-09-09 follow-up** (`20260909063711_fix_cto_report_automation_and_rollback_fabrication.sql`): the 2026-09-08 fix above did not fully hold — both the daily report and the board memo generated that same day still named six healthy automations as failing and the CTO report's Infrastructure Alerts still showed a fabricated "14.11% Breached" rollback rate. Root causes, found by verifying that day's actual reports against production:
  - `get_cto_daily_report` and `get_cto_diagnostics` both computed "failing automations" with `WHERE d.start_time >= v_end - interval '24 hours'` and **no upper bound** — a report regenerated or backfilled for a past `p_date` can pick up failures from after its own reporting window. Added `AND d.start_time <= v_end` to every jobs query in all three RPCs.
  - All three RPCs (`get_cto_daily_report`, `get_cto_diagnostics`, `get_cto_issue_intelligence`) INNER JOINed `cron.job_run_details` to `cron.job`, which silently drops any run whose job has no current `cron.job` row — e.g. `public.email_queue_dispatch()`, triggered ad-hoc via `cron.schedule_in_background` rather than on a fixed schedule. This was exactly backwards: email_queue_dispatch was canceled 26 times the week of 2026-09-08 (a real backlog of 509 pending emails) and was invisible in every report, while six unrelated, healthy named jobs got reported as failing instead. Switched to `LEFT JOIN`, deriving a `(unscheduled) <function_name>` label from the command text and grouping by that label (not by the ephemeral per-run `jobid`) so repeated ad-hoc failures collapse into one entry.
  - `get_cto_diagnostics` never got the day-over-day snapshot fix applied to `get_cto_daily_report` on 2026-09-08 — its "Transaction rollback rate" and "Deadlocks since boot" alert rows still read raw lifetime ratios straight from `pg_stat_database`. The lifetime rollback ratio (~14.2%, since the last stats reset) is what showed up in the CTO report as a false "Breached" P2 action item. Ported the same `db_stat_snapshots`-based day-over-day delta, reporting "Unavailable" (not a fabricated percentage) when no trustworthy same-day snapshot pair exists.
  - `get_cto_daily_report`'s own rollback gate only checked that counters moved forward, not that the baseline snapshot's `day` was actually `p_date - 1` — a multi-day gap in the snapshot cron would silently compute a multi-day rate and report it as one day's figure. Added an explicit day-adjacency check.
  - Sign-in "sessions" were counted by distinct `user_id`, populated on only ~10% of sign-in attempts (most are pre-authentication). Undercounted weekly session volume by ~14x while the success *rate* still looked plausible (52 sessions reported vs. 724 actual for the week of 2026-09-08, both around 82% success). Switched to `session_trace_id`, present on every attempt.
  - `db_stat_snapshots` had no column to store a daily deadlock count, so a real delta could never exist even with a correct gate. Added the `deadlocks bigint` column and started capturing it in the same daily upsert that already captures commits and rollbacks.
  - Verified post-fix against production for 2026-09-08: 0 of 152 scheduled automations failed (was reported as 6); email_queue_dispatch now surfaces correctly (4 failures in the 24h window, 26 over the week); rollback rate correctly reports "Unavailable" for that date; sign-in sessions correctly show 724 tried / 595 eventually succeeded.
  - Not fixed in this pass: `get_cto_issue_intelligence`'s slow-query classification still labels chronic, 30-day-old statements with plain `severity` text ("Critical" for >2000ms mean) with no accompanying "chronic, not new" framing at the RPC level — the edge function's rendering currently supplies that framing itself. Revisit if the rendered report starts treating these as same-day P1s again.
- **2026-09-16 accuracy pass** (`20260916060000_fix_cto_report_ok_status_and_slow_query_severity.sql`): triggered by verifying the 2026-09-15 daily report and week-ending-2026-09-15 board memo PDFs against live production. Found the exact regression the 2026-09-09 note above predicted, plus two more, all self-contradictory within their own PDF:
  - `get_cto_issue_intelligence`'s slow-query severity was in fact never capped — still `CASE WHEN mean_exec_time > 2000 THEN 'Critical'`, despite `daily-cto-report/index.ts` carrying a comment since 2026-09-09 asserting "the RPC now caps severity at 'Medium'/P3". Compounded by the edge function's own "Today" action-plan bucket being `i.eta === 'Today' || i.severity === 'Critical'` — so a Critical-severity slow query landed in "CTO Engineering Action Plan: Today" as a P1 same-day fire even though its own `eta` field said "Ongoing — chronic performance debt, not a same-day incident" one row over. Fixed both: RPC now caps at Medium/Low and emits explicit `priority`/`blocking_production`/`resolution_eta` fields; the edge function bucket now reads `eta === 'Today'` only (every other issue type already sets `eta:'Today'` precisely when severity is Critical, so this isn't a behavior change for them).
  - `get_cto_diagnostics`'s "Authentication Diagnostics" `failure_breakdown` counted every `login_phase_events` row with `status <> 'success'` as a sign-in failure. Only `phase = 'auth.signin.attempt'` uses the string `'success'`; every other phase (`auth.enforceAccountAccess.end`, `gate.account_frozen.check`, `gate.name_completion.check.end`, `gate.phone_collection.check.end`, `auth.getSession.end`, `guard.resolved`) reports its own success as `status = 'ok'`. On 2026-09-15 this miscounted ~26,500 routine "ok" checkpoint events as sign-in failures, making the report's own "Authentication Diagnostics" table imply ~28,000 failures in the same document whose dashboard tile (correctly phase-scoped) said 58 failures / 85.5% success. Fixed: exclude `'ok'` alongside `'success'`.
  - Board memo's "Financial controls automated: N of 165" indicator subtracted ALL of `failingJobs` (including ad-hoc/unscheduled invocations like `email_queue_dispatch`, which are never part of the 165 *scheduled* `cron.job` count) from `total_scheduled`. On a day where 0 of 165 scheduled jobs failed and only the unscheduled email dispatcher did, this rendered "164 of 165 — Below target", directly contradicting the memo's own headline sentence ("No financial-control automation is currently failing"). Fixed: the indicator now only subtracts `failingJobs` entries where `unscheduled !== true`.
  - Root cause behind "Unavailable" rollback rate / commits / deadlocks for the whole 2026-09-02 to 2026-09-15 window: the `capture-daily-cto-snapshot` cron job from the 2026-09-11 fix below was never actually live in production (repo migrations don't reliably auto-apply — see [[project_repo_migrations_diverge_from_production]]). Re-applied directly against prod; also caused a section-3 "Commits: 0 / Rolled-back txns: 0" fabrication in the edge function's own rendering (`fmt(null)` → `Number(null||0)` → "0") that contradicted section 27's correctly-labeled "Unavailable" for the same underlying gap — fixed by gating both KPI-card renderers on `I.rollback_trustworthy`.
  - Verified live against production during this pass: `capture-daily-cto-snapshot` now scheduled (jobid 39041, `55 20 * * *`); both RPC fixes confirmed present in `pg_proc.prosrc`. The board memo's sign-in-eventual-success figure (session_trace_id-keyed) and the SMS-confirmation "not being recorded" gate were independently re-verified against live data and are correct as-is — no fix needed there despite the 2026-09-09 gate-doc's stale variable-name check suggesting otherwise.
