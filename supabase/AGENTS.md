# Database decisions (read before changing `supabase/` or the client code that reads these functions)

Every rule below names one server function as the only place a figure or a status is decided. The
client displays what that function returns and never recomputes it.

More database rules live in `supabase/migrations/AGENTS.md`, `supabase/tests/AGENTS.md`, `supabase/functions/AGENTS.md` and `drizzle/migrations/AGENTS.md`; rules about the screens that read them are in `src/hooks/AGENTS.md`, `src/components/pipeline/AGENTS.md` and `src/components/executive/agent-ops/AGENTS.md`.

- Agent Monitoring repayment clocks come only from `am_plan_clock` / `am_plan_arrears` (read-only, staff-gated): a plan's clock starts the day AFTER its LAST landlord payout (status `awaiting_agent_receipt` or `completed`, Kampala date of `COALESCE(finops_disbursed_at, disbursed_at)`; a payout with neither stamp falls back to `otp_verified_at` and is counted in `landlord_paid_dates_estimated`), `outstanding_balance` plans keep `repayment_starts_on`, and a plan with no landlord payout has no clock (nothing expected) and is bucketed `tenant_paying_no_landlord` or `awaiting_landlord`. Never recompute the start date client-side.
- Agent Monitoring's every tab counts from the payout clock: the main tab, the two cohort tabs, Expected vs paid (`am_plan_positions`, same shape as `get_agent_monitoring_positions`) and Rent Analysis all use `am_plan_clock` and only the `counting` and `outstanding_balance` buckets; plans with no landlord payout have their own two tabs. The After / Before 1 Sep tabs split Rent Plans by `clock_start`, not by request or agent creation date. "Requests submitted" excludes rejected, cancelled and deleted_by_agent requests (all-time is the secondary line; live plans are shown separately). Who may read these figures is one function, `_am_staff_ok()`.
- Partner portfolios may have up to 2 extra payout numbers (`portfolio_payout_destinations`), written only by `set_portfolio_payout_destinations` (Admin/Partner Ops); proxy split withdrawals go only through `submit_proxy_split_withdrawal`, which validates ownership, amounts and balance server-side and creates one withdrawal request per number.
- `get_payables_predictive_forecast` reads `v_payables_lines`, `v_landlord_float_payables` and `v_landlord_payout_settlement` once per call through MATERIALIZED CTEs and runs with JIT off; re-expanding those views per period pushed it past the 8s API timeout.
- One-time codes never reach `sms_delivery_log` in clear: every sender logs through `functions/_shared/smsDeliveryLog.ts` (or wraps the body in `redactSmsCodes(...)` before a direct insert). The masking stays deliberately narrow — amounts, masked tails (`ending 9270`, `***457`) and the support number must keep rendering, so never broaden it to all digits.
- 360-day Rent Plans (migrations 2026-10-29, `v360_*`): new plans are stamped v360 only while `v360_settings.new_plans_enabled` is on (set via `v360_set_new_plans_enabled`); legacy plans never reprice. Funding opens schedules via `_v360_activate_core`, each `agent_collections` row on an active v360 plan records a split via `_v360_waterfall_core`, and the daily `v360-day30-settle-0630-eat` job records Day-30 cover and buffer draws. These are records only; ledger posting awaits CFO-approved categories. Read figures via `v360_plan_summary`. The approved cycle economics (tenant agent 8% of Gross = 6% sub-agent + 2% general, segregated Cover Pool, one-off Proxy Agent 2% of P from cycle 1 of that pool, tithe = 10% of Welile's 7%, partner capital and partner margin classified operating) are drafted in `docs/pending-migrations/20261102160000_v360_cycle_waterfall.sql` and `docs/pending-migrations/20261102160100_v360_ledger_categories_and_partner_onboarding.sql` and are not applied. The pure check is `v360CycleWaterfall` in `src/lib/contractEngine360.ts`. `new_plans_enabled` stays off. Legacy and non-v360 plans are not repriced.

- `sofp_ledger_legs` reads advance top-up legs as A10 and emits no X4 for bucket_reclass pairs (CFO approved 2026-10-01).
- `v_agent_daily_eligibility` falls back to LEAST(daily_repayment, outstanding) only when no pinned bill exists today/yesterday.
- Fingerprinted CFO packages (`cfo_bucket_a_post`, `cfo_corr_5300000_post`) post only via their own function: approver allowlist, own fresh preflight (<30 min), frozen lines, atomic.
- Welile Homes dues are exactly 12 per tenant: `welile_homes_monthly_dues.due_month_index` (1-12, unique with `tenant_id`). `enroll_welile_home_tenant` inserts months only on first enrolment; re-enrolment revises only untouched dues (pending, nothing collected, unpaid, no ledger id) and recomputes `receivable_total` from the 12 rows, so a rent change can never add, duplicate or reprice paid months.
- Instant bike collection is opt-in per plan (`merchandise_recovery_plans.instant_wallet_sweep`, changed only via CFO `cfo_set_bike_instant_sweep`): ledger trigger `trg_zzz_bike_instant_sweep` collects withdrawable cash-ins (never float, never `bucket_reclass_in`) before ROI advance recovery, which now also runs there for `return-cycle:` Returns with the same idempotency key; withdrawals/float conversion are refused while such a plan is owed.
- A funder's verified Rent Plan pack (landlord phone, payout mobile money, tenant agreement, funding timeline and receipt) comes only from `funder_verified_rent_plan_dossier`. Phone, mobile money and the agreement are empty unless the plan is verified and the caller funds it. The timeline says the rent was paid only when a landlord payout is completed, awaiting the agent receipt, or disbursed. An open float allocation is on the agent's dashboard. The landlord has a Welile account only by the same phone match as `get_my_landlord_properties`.
- Welile Cover on a direct mobile-money or cash rent payment is `self_support_proxy_fee` stored by `funder_record_offplatform_rent_payment` and taken from the partner wallet only by `staff_confirm_offplatform_rent_payment` / `staff_retry_offplatform_cover_fee`. A short balance waits. No proxy agent keeps the fee. The support-team option records nothing and charges nothing.
- Partner float release to an agent's landlord float is `_approve_pending_portfolio_core`. `approve_pending_portfolio` stays the Partner Ops wrapper. `funder_direct_release` (pipeline_switches, default off) makes `funder_support_tenant_direct` call the core in the same transaction when the partner's float covers the plan. Receivable mode still waits for the deposit, then the float-credit trigger calls the core. Plans with no assigned agent are excluded from `v_partner_self_fundable_plans` and refused by `funder_support_tenant_direct`. Frozen, held, suspended, and below-target agents are flagged in `funder_direct_release_flags` and do not stop the release. Today's direct releases are only `cfo_partner_released_today()`. The waiting backlog is `supabase/scripts/release_pending_partner_portfolios.sql`, which is not a migration.
