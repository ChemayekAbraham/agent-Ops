# Database decisions (read before changing `supabase/` or the client code that reads these functions)

Every rule below names one server function as the only place a figure or a status is decided. The
client displays what that function returns and never recomputes it.

- Agent Monitoring repayment clocks come only from `am_plan_clock` / `am_plan_arrears` (read-only, staff-gated): a plan's clock starts the day AFTER its LAST landlord payout (status `awaiting_agent_receipt` or `completed`, Kampala date of `COALESCE(finops_disbursed_at, disbursed_at)`; a payout with neither stamp falls back to `otp_verified_at` and is counted in `landlord_paid_dates_estimated`), `outstanding_balance` plans keep `repayment_starts_on`, and a plan with no landlord payout has no clock (nothing expected) and is bucketed `tenant_paying_no_landlord` or `awaiting_landlord`. Never recompute the start date client-side.
- Agent Monitoring's every tab counts from the payout clock: the main tab, the two cohort tabs, Expected vs paid (`am_plan_positions`, same shape as `get_agent_monitoring_positions`) and Rent Analysis all use `am_plan_clock` and only the `counting` and `outstanding_balance` buckets; plans with no landlord payout have their own two tabs. The After / Before 1 Sep tabs split Rent Plans by `clock_start`, not by request or agent creation date. "Requests submitted" excludes rejected, cancelled and deleted_by_agent requests (all-time is the secondary line; live plans are shown separately). Who may read these figures is one function, `_am_staff_ok()`.
- The Tenant Operations Workspace counts from the same payout clock as Agent Monitoring, only through the `*_amclock` functions (migration `20261012180000`; `tops_plan_clock_amclock`, `tops_open_instalments_asof_amclock`, `tops_arrears_ageing_amclock` and the rest of the 29 clones): every Workspace read of arrears, due, never-billed, ageing, calling queue, pipeline, shortfall or payment behaviour calls an `_amclock` RPC, never the original `tops_*` one. Plans in the `tenant_paying_no_landlord` / `awaiting_landlord` buckets owe nothing and appear only in `tops_landlord_not_paid_summary_amclock`; the 2 hand-set `override` rows in `tops_plan_clock` are kept as set. The original `tops_plan_clock`, `tops_resolve_plan_clock`, `tops_plan_instalments` and every existing `tops_*` function stay untouched (TenantOpsHome still uses them). Parity test: `supabase/tests/tops_amclock_parity.sql`.
- Tenant Ops Weekly Performance (Wed-Tue weeks) counts from the same payout clock, only through `get_tenant_ops_weekly_performance_amclock` / `get_tenant_ops_weekly_history_amclock` (migration `20261013160000`): a plan is active, paying, non-paying or 20+ days only from its `am_plan_clock` start, and plans in `tenant_paying_no_landlord` / `awaiting_landlord` are shown only as `landlord_not_paid_count`. Weeks before 2026-10-07 stay exactly as frozen in `tenant_ops_weekly_metrics` and are never rebuilt; weeks from 2026-10-07 are frozen in `tenant_ops_weekly_metrics_amclock` by `pin_tenant_ops_weekly_metrics_amclock_catchup`. `v_rent_plan_schedule` (shared with top-up eligibility), `v_tenant_ops_tenant_base` and the original weekly functions are not edited. Parity test: `supabase/tests/tenant_ops_weekly_amclock.sql`.
- The two Agent Monitoring uncovered-plan tabs read one RPC, `am_uncovered_plans(p_as_at, p_limit, p_offset)` (SECURITY DEFINER behind `_am_staff_ok()`, paged), never client-side joins of rent plans, payouts and float allocations. A daily job (`am_detect_clock_drift`, 06:00 Kampala; migration `20261013180000`) compares `am_plan_clock` with what the Workspace and Weekly Performance counted and appends differences to `am_clock_drift_runs` / `am_clock_drift_daily` (append-only; a `system_event` is emitted when plans differ). Agent Monitoring shows the result as "Pages agree / N plans differ" and all three pages carry the one explainer sentence from `src/lib/payoutClockExplainer.ts`. Never insert into `tops_plan_clock` to fix a missing start; the `_amclock` functions already include those plans. Tests: `supabase/tests/am_hardening.sql`; reconciliation: `docs/three-pages-reconciliation.md`.
- "Days without payment" is a parameter, not a constant: the No Payment report reads `get_tenant_ops_no_payment_report_v2(p_min_days, p_agent_id)` (1 to 365, anything else raises; at 20 it equals the original `get_tenant_ops_no_payment_report` exactly) and the Weekly Performance page's extra "N+ days (calculated now)" card reads `get_tenant_ops_dormant_amclock(p_min_days)` on the payout clock (migration `20261013220000`; read-only, plans whose landlord is not paid are never counted). The number lives in the URL as `?days=` (`useNoPaymentDays`, `src/lib/noPaymentDays.ts`); the bands are N+, N+10, N+20. The frozen weekly record (`tenant_ops_weekly_metrics`, `tenant_ops_weekly_metrics_amclock`, the "20+ Days No Payment" card and the history) stays fixed at 20 and past weeks are never rebuilt; the original report function and the weekly / pin functions are not edited. Test: `supabase/tests/tenant_ops_no_payment_threshold.sql`.
- Tenant classification (Active / Waiting for landlord payment / Dormant / Inactive, plus a "Needs review" flag) lives only in `tops_tenant_classification_summary()` and `tops_tenant_classification_list(...)` (migration `20261013201000`, SECURITY DEFINER, `_am_staff_ok()` gate, read-only), built on `_am_plan_clock_core` so the Active / Waiting split uses the shared payout clock. The Tenant Classification tab in the Tenant Operations Workspace only displays what they return (`src/hooks/useTenantClassification.ts`, `src/lib/tenantClassification.ts`); never recompute a category, a start date or a completion date in the client, and never add a second definition. First match wins: Active (counted plan still owing) > Waiting (plan with no counted landlord payout) > Dormant (completed or fully repaid, nothing running; `completed_on` is the date of the last payment) > Inactive. Test: `supabase/tests/tops_tenant_classification.sql`.
- Tenant payment score (`tenant_payment_score(uuid[])`, migration `20261014100000`; SECURITY DEFINER, `_am_staff_ok()` gate, read-only) is the only place a tenant's score, label (`proven_good` / `good_agent_pick` / `average` / `watch`) and reason are decided; never recompute them in the client. History tenants: 40 paid/owed (`am_plan_arrears`, counted plans only), 25 on-time days, 15 completed plans, 10 self-paid (`collection_channel = 'tenant_deposit_auto'`), 10 no 20+ day gaps; new tenants: 60 agent portfolio paid/owed, 40 `welile_trust_score_cache` (0 to 100). Reversed collections and plans whose landlord is not paid are ignored. `tenant_payment_score_daily` is append-only (written only by the 00:45 Kampala job `tenant_payment_score_run`, one row per tenant per day, staff read); never update or delete its rows. Test: `supabase/tests/tenant_payment_score.sql`.
- Rent-request desks are ordered by the server, through one RPC: `rent_request_desk_order(p_request_ids, p_sort)` (migration `20261014140000`; SECURITY DEFINER, read-only, STABLE). It ranks the requests a desk has ALREADY loaded and joins the tenant payment score (`_tenant_payment_score_core`) to each; "best_payers" (the default: score high to low, then oldest first, then id), "newest" and "oldest". `RentPipelineQueue` (every stage), `useServiceCenterRentQueue` and `useTenantPipelineHubData` all go through `src/hooks/useRentDeskOrder.ts`; never compute or compare a score, or add a second ranking, in the client, and never change which rows a desk loads to sort it (each desk keeps its own limit and pagination). A failed ordering call leaves the desk in its previous order. Desk roles (the `_am_staff_ok()` roles plus landlord_ops and partner_ops) may rank any request; a Service Center manager only requests routed to them. It is not called by, and does not call, any status-transition or approval function. The same RPC does the desks' filters and their count (migration `20261014180000`): `p_labels` (proven_good, good_agent_pick, average, watch), `p_arrived` (today, 7d, custom with `p_from` / `p_to`; arrival = the Kampala day the request was created; 7d = the last 7 Kampala days, today included) and it returns `matches`, `match_count` and `total_count`; a desk hides the rows with `matches = false`, shows `match_count` as its count and never evaluates a label or a date itself. The sort and filters live in the URL (`desk_sort`, `desk_labels`, `desk_arrived`, `desk_from`, `desk_to`) through `useRentDeskUrlState` / `src/lib/rentDeskFilters.ts`; the controls and the label chip with its reason are `src/components/rent-desk/RentDeskControls.tsx` and `PaymentLabelChip.tsx`, and every desk uses them. The reason line says "Rent Plan". The CFO payout desk (`RentDisbursementQueue`, minute 001/08) uses the same server order and controls: best payers first by default, each agent's tenants listed in that order and the agents by their best-ranked tenant (`src/lib/payoutDeskGrouping.ts`; with no server order it keeps its old newest-first layout). It sets the order and visibility only; selection, the batch review and every payment step are unchanged, and selection is cleared when a filter changes. Test: `supabase/tests/rent_request_desk_order.sql`.
- Smartphone usage under the Tenant Operations Workspace's "Tenant Classification" tab comes only from `tops_smartphone_usage(p_from, p_to)` (migration `drizzle/migrations/0566_tops_smartphone_usage.sql`; STABLE SECURITY DEFINER, `_am_staff_ok()` gate, read-only, granted to authenticated/service_role only): the all-time declared (`profiles.has_smartphone`) and confirmed (`profiles.smartphone_status`) split never follows the date filter, while the joined cohort and the `tenant_dashboard_access_log` device counts are counted over Kampala days taken from the URL (`tc_range`, `tc_from`, `tc_to`) and clamped by `kampalaWindow` in `src/lib/tenantSmartphoneUsage.ts`; the client never counts a device or a day itself, and `tops_tenant_classification_*` categories, counts and the list stay untouched. Test: `supabase/tests/tops_smartphone_usage.sql` (needs a role with EXECUTE; the read-only query console cannot run it).
- A Rent Plan renewal can be made at any rent and any allowed number of days, and the server's advice on the amount is advisory, never a limit (`get_renewal_advice`, `preview_renewal_amount`, `renew_rent_request`; migration `20261014200000`). Any positive rent is accepted and the days must pass `_rent_days_allowed` (the live `rent_requests_duration_days_check`: 30, 60, 90, 120 or a multiple of 7 from 7 to 364); fees, total and daily payment are always recomputed by the existing pricing trigger. Changing the rent OR the days REQUIRES a reason code (`landlord_raised`, `moved_house`, `tenant_requested_lower`, `other`) and an explanation of at least `min_explanation_length` characters (system_config `rent_renewal_advice_params`, default 10), else `RENEWAL_EXPLANATION_REQUIRED`; the advice is recomputed in the function for the chosen days and stored with the explanation on the NEW request (`renewal_*` columns, written once, readable by every pipeline reviewer through the normal request read), together with `renewal_above_suggestion` / `renewal_above_by` when the rent is above `suggested_max_rent`. The previous plan is never updated: a renewal only reads it and inserts a new request. The tenant's OTP is bound to the new rent AND days (`RENEWAL_OTP_MISMATCH`), and reviewer notes go through `add_rent_request_review_note` into the append-only `rent_request_review_notes`. Why: agents know things the payment history cannot (a landlord raising rent, a move), so a hard cap would push renewals off the platform, while a recorded reason keeps every above-advice renewal reviewable and the earlier plan's figures untouched. The Rent Access Limit used in the advice is `rent_access_limit_server(tenant)`, which must match `src/lib/rentAccessLimit.ts` exactly (fixtures regenerate with `npx vite-node supabase/tests/fixtures/gen_rent_access_limit_fixtures.ts`). Tests: `supabase/tests/rent_renewal_any_rent_days.sql`, `supabase/tests/rent_access_limit_server.sql`, `src/__tests__/renewalOtpSms.test.ts`.
- A landlord's Rent Plans and the two Landlord Ops "paid" lists are read through two functions and nowhere else (migration `20261015100000`; SECURITY DEFINER, STABLE, read-only, `search_path = public`, granted to `authenticated` only): `landlord_tenant_overview(p_landlord_id)` gives one row per Rent Plan with the tenant, the money, the agents and a plain `funding_stage`, and `landlord_ops_paid_lists(p_tab, p_search, p_limit, p_offset)` gives the `paid_repaying` list (landlords who received money and have at least one repaying tenant) and the `completed` list (a completed plan and no funded or repaying plan) with the size of both tabs. Only Landlord Ops, COO, CFO, CEO and super admin may call them (checked in the function with `has_role`, not `is_ops_role()`). The funding stage is decided only there, from the plan status plus `agent_landlord_float_allocations` (cancelled ones ignored): rejected / cancelled / deleted_by_agent = "Rejected/Cancelled", completed = "Completed", repaying = "Repaying", funded with a fully paid allocation = "Landlord paid", other funded = "Funded – money with agent", every earlier status = "In review" (the dash is an en dash); never recompute a stage, a list or a tab count in the client. Each list row also carries `tenant_count`, `total_rent`, `total_repaid`, `balance_left` (every Rent Plan except rejected, cancelled and deleted ones, so it equals the Tenants section's total line), the landlord's registering agent and the verified flag (migration `20261015140000`); the Landlords page shows them as the "Paid & Repaying" and "Completed" tabs and never adds them up itself. They add nothing to the existing Landlord Ops tab counts and move no money. Test: `supabase/tests/landlord_tenant_overview.sql`.
- Whether an approved portfolio belongs in the Invited Portfolios pipeline (and how many times its invite email went out) is decided only by `partner_ops_invite_visibility(p_portfolio_ids)` (migration `drizzle/migrations/0577_partner_ops_invite_visibility.sql`; STABLE SECURITY DEFINER, read-only, `search_path = public`, granted to `authenticated` only): `invited` is true when a `portfolio_completion_tokens` row exists OR a `partner-portfolio-invite` email was logged for the portfolio code, and the same result carries the token expiry/consumption stamps and the delivery count/time/status. Only Partner Ops, COO, CFO, CEO, manager and super admin may call it (checked in the function with `has_role`). The panel (`src/components/executive/InvitedPortfoliosPanel.tsx`) must call this RPC and never read `portfolio_completion_tokens` or `email_send_log` directly — their RLS only lets partners read their own token and nobody read the send log, which is what made the Approved filter show 0. Test: `supabase/tests/partner_ops_invite_visibility.sql`.
- The partner name, phone and email behind each row of the Invited Portfolios panel come only from `partner_ops_invite_partners(p_portfolio_ids)` (migration `drizzle/migrations/0578_partner_ops_invite_partners.sql`; STABLE SECURITY DEFINER, read-only, `search_path = public`, granted to `authenticated` only): one row per requested portfolio with the partner's display name (`profiles.full_name`, falling back to their email, then `Unnamed partner`), phone, email, and `in_pending_queue` (the portfolio already sits in `funder_pending_portfolios` as `pending`, so the invite pipeline must drop it). Only Partner Ops, COO, CFO, CEO, manager and super admin may call it (checked in the function with `has_role`). `src/components/executive/InvitedPortfoliosPanel.tsx` must call this RPC instead of reading `profiles` or `funder_pending_portfolios` with an `in.()` filter — with 1,000+ ids that request URL is rejected (HTTP 400 past roughly 600 ids) and the panel silently showed "—" for every partner. A role without the gate may only fall back to batched reads of at most 200 ids per request. Test: `supabase/tests/partner_ops_invite_partners.sql`.
- The Landlord Ops home figures for a date range come from one function, `ops_landlord_ops_home_range(p_start, p_end)` (migration `20261015160000`; SECURITY DEFINER, STABLE, read-only, `search_path = public`; authenticated only; landlord_ops, coo, cfo, ceo, manager, super_admin, with a missing user refused first), modelled on `ops_tenant_ops_home_range`. The range is Kampala days (start of the day of `p_start` to the end of the day of `p_end`). Landlords whose phone (last 9 digits, `normalize_phone_last9`) matches a profile with `deleted_at` set are left out of every figure (the per-agent float balance cannot be narrowed that way). One definition per figure, each reusing the one the screens already use, and the client never recomputes one: total (created before the end of the range) and new (created in it); verified in range = status verified in `v_landlord_ops_status` with state date `COALESCE(verification_updated_at, created_at)` in range; pending verification = the current queues exactly as `src/hooks/landlordOpsQueueFilters.ts` defines them (houses, landlords, LC1; not range-based); with / without tenants = `v_landlord_ops_status.has_tenant`; funded in range = distinct landlords with a Rent Plan whose `funded_at` is in range (as `ops_landlord_funded_stats`); landlords paid = distinct landlords with a `landlord_payouts` row that is not failed, disbursed in range (`COALESCE(finops_disbursed_at, disbursed_at)`) and not reversed (all its receipts reversed and none active); principal recovered = `instalment_allocations.principal_component` not reversed with `instalment_date` in range (as `landlord_ops_principal_comparison`); float balance = `agent_landlord_float.balance` above 0 (as `landlord_ops_float_overview`); missing GPS = no latitude or no longitude; missing payout details = neither a mobile money number nor a bank name; duplicate phones = last-9-digit numbers held by more than one landlord. Test: `supabase/tests/ops_landlord_ops_home_range.sql`.
- The first seven days of every new Rent Plan are read through three functions and nowhere else (migration `20261015180000`; SECURITY DEFINER, STABLE, read-only, `search_path = public`; authenticated only; `auth.uid()` plus `_am_staff_ok()` or SQLSTATE 42501, checked before any argument): `am_new_tenant_first7_v2(p_from, p_to, p_frequency, p_agent_id)` (one row per plan), `am_new_tenant_first7_summary_v2(...)` (the same rows added up, never a second calculation) and `am_new_tenant_first7_payments(p_rent_request_id)` (the collections behind the grid). Plans are funded / repaying / completed, in `_am_plan_clock_core` buckets counting / outstanding_balance, with `first_landlord_paid_on` (a Kampala date) in the range of at most 31 days (else 22023). Day 1 = first_landlord_paid_on + 1, days 1 to 7. Frequency is `rent_requests.repayment_frequency` (empty = daily), never `tops_plan_clock.cadence`. Paid = non-reversed `agent_collections.amount` by Kampala date. Due: daily = `daily_repayment` each day; weekly = `daily_repayment` x 7 on day 1 only (0 on days 2 to 7); never above `total_repayment`. Day state: `future` (after today, or today with nothing paid), `not_due`, `paid`, `part`, `missed`. `expected_to_date` = due over the days before today. Row status: `too_early` (day 1 after today), `not_started` (nothing paid), `on_track` (paid_7d >= expected_to_date), `behind`. Don't recompute any of this in the client and don't change `am_new_tenant_first7` for it. Test: `supabase/tests/am_new_tenant_first7_v2.sql`; rollback: `supabase/rollbacks/20261015180000_am_new_tenant_first7_v2.rollback.sql`.
- The Agent Ops network overview for a date range comes from one function, `get_agent_ops_network_overview(p_start, p_end, p_min_expected default 50000)` (migration `20261015200000`; SECURITY DEFINER, STABLE, read-only, `search_path = public`; authenticated only; the role check is copied from `get_agent_ops_overview`, so a missing user is `auth_required` and anything but is_ops_role / manager / cfo / ceo / coo / cto / super_admin is `not_authorized`; p_end may not be a future Kampala day). The agent set is `agent_ops_qualifying_agent_ids()` less deleted accounts (profiles.deleted_at or an un-restored soft_deleted `deleted_accounts` row), each person once; the agent on a request is `COALESCE(assigned_agent_id, agent_id)` and never the tenant. `counts` are all-time snapshots (`posted_requests` and `approved_agents` count AGENTS), `approved` follows the range (dated `COALESCE(cfo_reviewed_at, funded_at)`; its receivables are the `rent_plan` rows of `v_receivables_lines`), the live book is funded / repaying and not ended. Don't recompute any of this in the client. Test: `supabase/tests/agent_ops_network_overview.sql`; rollback: `supabase/rollbacks/20261015200000_agent_ops_network_overview.rollback.sql`.

- The all-time rent request cards of the Tenant Ops summary ("Rent request journey" and "Financed: repayment outcome") come only from `tenant_ops_rent_request_lifetime()` (migration `20261016200000`; SECURITY DEFINER, STABLE, read-only, `search_path = public`; no arguments and no dates; authenticated only; the same role check as `ops_tenant_ops_home_range`: is_ops_role, manager, super_admin, cto, ceo or coo with an enabled role, else 42501).
