# Agent Ops database figures

- The first seven days of every new Rent Plan are read through three functions and nowhere else (migration `20261015180000`; SECURITY DEFINER, STABLE, read-only, `search_path = public`; authenticated only; `auth.uid()` plus `_am_staff_ok()` or SQLSTATE 42501, checked before any argument): `am_new_tenant_first7_v2(p_from, p_to, p_frequency, p_agent_id)` (one row per plan), `am_new_tenant_first7_summary_v2(...)` (the same rows added up, never a second calculation) and `am_new_tenant_first7_payments(p_rent_request_id)` (the collections behind the grid). Plans are funded / repaying / completed, in `_am_plan_clock_core` buckets counting / outstanding_balance, with `first_landlord_paid_on` (a Kampala date) in the range of at most 31 days (else 22023). Day 1 = first_landlord_paid_on + 1, days 1 to 7. Frequency is `rent_requests.repayment_frequency` (empty = daily), never `tops_plan_clock.cadence`. Paid = non-reversed `agent_collections.amount` by Kampala date. Due: daily = `daily_repayment` each day; weekly = `daily_repayment` x 7 on day 1 only (0 on days 2 to 7); never above `total_repayment`. Day state: `future` (after today, or today with nothing paid), `not_due`, `paid`, `part`, `missed`. `expected_to_date` = due over the days before today. Row status: `too_early` (day 1 after today), `not_started` (nothing paid), `on_track` (paid_7d >= expected_to_date), `behind`. Don't recompute any of this in the client and don't change `am_new_tenant_first7` for it. Test: `supabase/tests/am_new_tenant_first7_v2.sql`; rollback: `supabase/rollbacks/20261015180000_am_new_tenant_first7_v2.rollback.sql`.
- The Agent Ops network overview for a date range comes from one function, `get_agent_ops_network_overview(p_start, p_end, p_min_expected default 50000)` (migration `20261015200000`; SECURITY DEFINER, STABLE, read-only, `search_path = public`; authenticated only; the role check is copied from `get_agent_ops_overview`, so a missing user is `auth_required` and anything but is_ops_role / manager / cfo / ceo / coo / cto / super_admin is `not_authorized`; p_end may not be a future Kampala day). The agent set is `agent_ops_qualifying_agent_ids()` less deleted accounts (profiles.deleted_at or an un-restored soft_deleted `deleted_accounts` row), each person once; the agent on a request is `COALESCE(assigned_agent_id, agent_id)` and never the tenant. `counts` are all-time snapshots (`posted_requests` and `approved_agents` count AGENTS), `approved` follows the range (dated `COALESCE(cfo_reviewed_at, funded_at)`; its receivables are the `rent_plan` rows of `v_receivables_lines`), the live book is funded / repaying and not ended. The collection rate reads the command centre's pinned expected from `agent_expected_day_plans` and never calls `pin_agent_expected_day` (the function writes nothing; `range.days_without_pin` says how many days had no pin). Default rate = payout-clock arrears (`_am_plan_arrears_core` as at today) / outstanding; agents under `p_min_expected` are not ranked. `tops_smartphone_usage` has no agent-level figure, so it is returned unchanged as `smartphone_usage`. Don't recompute any of this in the client. Test: `supabase/tests/agent_ops_network_overview.sql`; rollback: `supabase/rollbacks/20261015200000_agent_ops_network_overview.rollback.sql`.
- The Agent Ops metrics (network totals, per-agent table, location breakdown, map pins, main-agent teams) come only from `agent_ops_metrics_totals`, `agent_ops_metrics_agents`, `agent_ops_metrics_locations`, `agent_ops_metrics_pins` and `agent_ops_metrics_main_agents` (migration `20261016100000`; SECURITY DEFINER, STABLE, read-only, `search_path = public`; authenticated only; agent_ops, coo, ceo, cto, manager and super_admin with `user_roles.enabled`, else 42501 before any argument is read; bad arguments are 22023 with a code such as RANGE_INVALID, SCOPE_INVALID, SORT_INVALID, LEVEL_INVALID or BOX_INVALID). They are the only definition of these figures: all of them sit on the owner-only helpers `_aom_scope`, `_aom_rows` and `_aom_allowed`, so a total can never differ from the sum of its rows. Dates are Kampala days; deleted accounts (`profiles.deleted_at` or an un-restored soft_deleted `deleted_accounts` row) are left out; houses are `house_listings` created in the range (verified / pending / with GPS from the listing, rejected from `agent_listing_rejections`). Listing money comes ONLY from `general_ledger` (`v_general_ledger_operational` wallet cash_in `agent_commission_earned` from `listing_bonus_approvals` plus `agent_commission` from `house_listings`; clawbacks are `listing_rejection_recovery` and `listing_rejection_offset`; `admin_correction` and reversed legs are out) and NEVER from `agent_earnings`, which is incomplete. Advances given and repaid are for advances issued in the range; outstanding and overdue are today's balances. Don't recompute any of it in the client and don't change or replace these functions for another screen: add a new function instead. Test: `supabase/tests/agent_ops_metrics.sql`; rollback: `supabase/rollbacks/20261016100000_agent_ops_metrics.rollback.sql`.
- The Agent Ops listing-quality and risk figures (approval rate, average days to verify, houses currently rejected, occupied vs empty, earnings per approved house, the longest-waiting pending houses; advances with no listing, advance outstanding against listing earnings with its flag, inactive listers, never-listed sub-agents, teams that owe most) come only from `agent_ops_metrics_listing_quality` and `agent_ops_metrics_risk` (migration `20261016190000`; SECURITY DEFINER, STABLE, read-only, `search_path = public`; authenticated only; same role gate and error codes as the first five metrics functions; both return jsonb). They are the only definition of these figures and are built on `_aom_rows(..., 'all')` / `(..., 'linked')`, so they inherit every rule of the metrics rule above (Kampala days, deleted accounts out, listing money from the ledger only, never `agent_earnings`). "Currently rejected" is a listing that is not verified and has status `rejected` (verified + pending + currently rejected = listed); it is not `agent_listing_rejections`, which counts rejection events in the range. Advance outstanding here is the full book and is not changed to match the Advance Repayment Monitor, which leaves out advances repaid from Returns (open question for Agent Ops / Finance in `docs/TOPS_BUILD_LOG.md`). Do not change or replace these functions for another screen: add a new one. Test: `supabase/tests/agent_ops_metrics_quality_risk.sql`; rollback: `supabase/rollbacks/20261016190000_agent_ops_metrics_quality_risk.rollback.sql`.
