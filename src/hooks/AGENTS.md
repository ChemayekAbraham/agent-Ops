# Forecast hooks

- `get_my_agent_vetting`, `agent_vetting_parent_id_link_state` and the agent vetting writes (`agent_vetting_confirm_phone`, `agent_vetting_confirm_email`, `agent_vetting_save_residence`, `agent_vetting_capture_gps`, `agent_vetting_save_details`, `agent_vetting_request_parent_id_link`, `submit_agent_vetting`) run only when `useAuth().enabledRoles` contains `agent` (real `user_roles.enabled = true` rows, the same list the CRM inbox and merchant float positions use, never the synthetic dashboard `agent`). While that list is still loading the queries stay off. A signed-in user without that role gets a neutral not-applicable state and is sent away from `/dashboard/agent/verification`; the dashboard banner stays hidden. Agent Ops review (`agent_vetting_queue`, `agent_vetting_detail`, `decide_agent_vetting`) is a different gate and is unchanged.
- `get_merchant_float_positions` runs only when `useAuth().enabledRoles` (real `user_roles.enabled = true` rows, the same list the CRM inbox uses, never the synthetic dashboard `agent`) contains cfo, financial_ops, manager, super_admin, ceo, or coo. `cto` is not included. A 400/403/P0001 "Not authorized" stops retry and polling. `my_awareness_calls_summary` / `my_awareness_calls_log` use that same enabled-role list for tenant_ops, landlord_ops, agent_ops, operations, manager, super_admin, coo, ceo, cto, and cfo; anyone else is fetched once (they may be a service-centre manager) with no retry or polling, and "not authorized" renders an empty state.
- Receivables Forecast uses read-only history averages for Behavior and both fixed-date scheduled amounts and recorded daily-installment amounts from get_receivables_forecast for Ideal; generate windows independently of the predictive RPC's 60-period cap and split contract reads into non-overlapping windows at its 400-day limit, so long horizons are not truncated or double-counted.
- Load 60 daily or 12 monthly historical periods for Receivables Behavior, averaging same weekdays from complete Monday–Sunday weeks or complete months only; the RPC limits history by the requested period count, and incomplete current periods understate collections.
- Rent-request desks are ordered by the server, through one RPC: `rent_request_desk_order(p_request_ids, p_sort)` (migration `20261014140000`; SECURITY DEFINER, read-only, STABLE). It ranks the requests a desk has ALREADY loaded and joins the tenant payment score (`_tenant_payment_score_core`) to each; "best_payers" (the default: score high to low, then oldest first, then id), "newest" and "oldest". `RentPipelineQueue` (every stage), `useServiceCenterRentQueue` and `useTenantPipelineHubData` all go through `src/hooks/useRentDeskOrder.ts`; never compute or compare a score, or add a second ranking, in the client, and never change which rows a desk loads to sort it (each desk keeps its own limit and pagination). A failed ordering call leaves the desk in its previous order. Desk roles (the `_am_staff_ok()` roles plus landlord_ops and partner_ops) may rank any request; a Service Center manager only requests routed to them. It is not called by, and does not call, any status-transition or approval function. The same RPC does the desks' filters and their count (migration `20261014180000`): `p_labels` (proven_good, good_agent_pick, average, watch), `p_arrived` (today, 7d, custom with `p_from` / `p_to`; arrival = the Kampala day the request was created; 7d = the last 7 Kampala days, today included) and it returns `matches`, `match_count` and `total_count`; a desk hides the rows with `matches = false`, shows `match_count` as its count and never evaluates a label or a date itself. The sort and filters live in the URL (`desk_sort`, `desk_labels`, `desk_arrived`, `desk_from`, `desk_to`) through `useRentDeskUrlState` / `src/lib/rentDeskFilters.ts`; the controls and the label chip with its reason are `src/components/rent-desk/RentDeskControls.tsx` and `PaymentLabelChip.tsx`, and every desk uses them. The reason line says "Rent Plan". The CFO payout desk (`RentDisbursementQueue`, minute 001/08) uses the same server order and controls: best payers first by default, each agent's tenants listed in that order and the agents by their best-ranked tenant (`src/lib/payoutDeskGrouping.ts`; with no server order it keeps its old newest-first layout). It sets the order and visibility only; selection, the batch review and every payment step are unchanged, and selection is cleared when a filter changes. Test: `supabase/tests/rent_request_desk_order.sql`.
- The collection percentage of the agent who registered a rent request (sub-agent or not: `rent_requests.agent_id`) for the current Thursday-Wednesday week, as shown on the rent request desks (Agent Ops, Tenant Ops, Landlord Ops, Partner Ops, COO, CFO, Service Center), comes only from `rent_request_agent_week_pct(p_request_ids)` (migration `20261026170000`; SECURITY DEFINER, STABLE, read-only, `search_path = public`; authenticated only, the same desk gate as `rent_request_desk_order`, at most 5000 request ids per call). It reads the same pieces the agent's own Weekly performance screen reads (`_agent_rule_week_start`, `_agent_weekly_plan_lines`, `_agent_weekly_posting_result`) and is tested equal to `get_my_weekly_performance` for every agent returned. The percentage is collected from Thursday THROUGH YESTERDAY (Kampala) divided by expected (billed) over the same days (`in_window_collected` / `in_window_due_so_far`, and the expired equivalents; migration `20261026190000`), to one decimal, on current Rent Plans (expired Rent Plans as a second figure). Today is left out on purpose because agents are still collecting; both amounts restart every Thursday, so on a Thursday there is no figure. Never recompute it in a desk, never include today, and never divide by a projected full-week due. The desks' default sort `agent_week` (highest first) is arranged on the desk from that function; the server order underneath is `best_payers`.
