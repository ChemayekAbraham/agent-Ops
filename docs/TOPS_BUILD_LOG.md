Root cause is a pre-existing, schema-wide `ALTER DEFAULT PRIVILEGES ... FOR ROLE postgres IN SCHEMA public GRANT ALL ON TABLES TO authenticated, service_role, ...` entry in `pg_default_acl` (confirmed present before this migration ran, and not something a `CREATE TABLE ... REVOKE ALL FROM PUBLIC ... GRANT SELECT` sequence can suppress, since it targets `PUBLIC`, not the already-privileged `authenticated` role specifically). This is a database-wide default, not something introduced by this migration — the same default ACL applies to every new table any future `tops_*` migration creates. In practice this is inert: RLS is enabled on all three tables and only a SELECT policy exists, so Postgres denies INSERT/UPDATE/DELETE for `authenticated` by default (no policy matches those commands), giving the same effective no-write-access outcome the rules ask for. Changing the default ACL itself would mean altering an existing, schema-wide object outside `tops_*`, which rule 2 forbids — recorded here rather than acted on.

## 2026-09-26 — `20260926170000_tops_plan_clock_resolver_functions.sql`

**Objects added:**

- `public.tops_resolve_plan_clock(uuid) RETURNS void` — upserts one `tops_plan_clock` row from `rent_requests` + `landlord_payouts`. `clock_start`/`clock_source`: `MIN(landlord_payouts.otp_verified_at)` for that plan (Kampala date) when present → `landlord_receipt`; else `COALESCE(funded_at, disbursed_at, created_at)` (Kampala date) → `funded_at`. Deliberately never reads or writes `rent_requests.repayment_starts_on`. `cadence`/`cadence_source`: `explicit`/(`daily`|`weekly`) only when `repayment_frequency_locked = true` AND `repayment_frequency IN ('daily','weekly')`; everything else (unlocked, or locked `monthly`) resolves to `unknown`/`unknown` — deliberately conservative, matching FINDINGS §3's warning not to copy the existing weekly-shape heuristic. A row already at `clock_source = 'override'` is left untouched (checked before computing, and re-guarded in the `ON CONFLICT ... WHERE` clause).
- `public.tops_build_plan_instalments(uuid) RETURNS integer` — regenerates `tops_plan_instalments` for one plan from its `tops_plan_clock` row. `daily`: one row per day, `clock_start+1..clock_start+duration_days`, amount = `daily_repayment`, last absorbs the remainder to hit `total_repayment` exactly. `weekly`: one row every 7 days, `ceil(duration_days/7)` rows, amount = `daily_repayment*7`, same remainder-absorbing last row. Returns 0 and writes nothing when cadence is `unknown`. Upserts by `(rent_request_id, seq)` so seq stays stable across reruns; only trims a trailing row from a previously-longer schedule when that row carries no `tops_instalment_settlements` row, so a rerun can never orphan settlement history.
- `public.tops_build_schedules_batch(integer DEFAULT 500) RETURNS integer` — the cron entry point. Scans `rent_requests` with `status IN ('funded','repaying')` that have no `tops_plan_clock` row yet, no `tops_plan_instalments` rows yet, or whose `updated_at` is newer than their `tops_plan_clock.updated_at`; calls the two functions above for up to `p_limit` of them, oldest-changed first.

All three: `SET search_path = public`, `SECURITY DEFINER` (owned by the same role as the `tops_*` tables, so they can write despite RLS), and — this matters — `REVOKE ALL ... FROM PUBLIC, anon, authenticated` explicitly naming `anon`/`authenticated`, not just `PUBLIC`. No EXECUTE grant to any client-facing role; these are internal-engine functions only reachable via the cron job.

**Cron jobs added:** `tops-build-plan-schedules-every-30min`, schedule `*/30 * * * *`, command `SELECT public.tops_build_schedules_batch(500);`. No existing job touched.

**Verified live** (project `43e6c2e1-18a6-4503-badb-5bb6c23491cc`): all three functions exist (`to_regprocedure`); the cron job is registered and `active`; ran `supabase/tests/tops_plan_clock_and_instalments.sql` directly against production inside a `BEGIN; SET LOCAL session_replication_role = replica; ... ROLLBACK;` block (self-cleaning, no permanent write) — all three cases passed: a 30-day daily plan (30 instalments, exact sum, remainder-absorbing last row), a 90-day weekly plan (13 instalments via `ceil(90/7)`, exact sum, remainder-absorbing last row, `weekly_due_dow` set), and an unlocked plan (cadence resolves to `unknown`, zero instalment rows written). Also ran `tops_build_schedules_batch(2)` directly against two real, live `funded`/`repaying` plans inside a rolled-back transaction — both resolved cleanly to `cadence = unknown` (expected: 815 of 820 active plans are unlocked per FINDINGS §3), confirming the batch function runs end-to-end against real data without error.

## 2026-09-26 — `20260926180000_tops_collection_allocation_functions.sql`

**Objects added:**

- `public.tops_is_collection_reversed(uuid) RETURNS boolean` — `agent_collections.reversed_at IS NOT NULL`, per FINDINGS §5's documented rule (deliberately not the `notes` text-marker check `rent_apply_collections_to_days()` uses, which FINDINGS measured as missing 48 reversed collections). One place to change if reversal is ever recorded differently.
- `public.tops_allocate_collection(uuid) RETURNS integer` — allocates one `agent_collections` row across its plan's `tops_plan_instalments`, oldest `due_date` first, `take = LEAST(remaining, instalment_outstanding)`. Recomputes from scratch on every call: excludes the collection's own existing rows when computing each instalment's outstanding room (so it never double-subtracts its own prior contribution), upserts by `(instalment_id, collection_id)`, then deletes any of its own rows the fresh computation no longer touches. A reversed collection releases (`released_at = now()`) instead of allocating, and never allocates once reversed. Returns 0 for a collection with no `rent_request_id`.
- `public.tops_allocate_pending(integer DEFAULT 2000) RETURNS integer` — the cron entry point. Candidate set: any non-reversed collection whose unreleased settlement total is still less than its own `amount` (this includes, but is not limited to, a collection with zero settlement rows — see the interpretation note below), plus any reversed collection that still has an unreleased settlement to release. Processes oldest `created_at` first.

All three: `SET search_path = public`, `SECURITY DEFINER`, `REVOKE ALL ... FROM PUBLIC, anon, authenticated` (the explicit anon/authenticated revoke, per the fix recorded in the previous entry). None of the three writes to `agent_collections`, `general_ledger`, or any wallet table, and none adds a trigger to any of them — confirmed by inspection of the migration's own SQL (the only `INSERT`/`UPDATE`/`DELETE` targets in it are `tops_instalment_settlements`).

**Interpretation flagged, not silently assumed:** the brief says `tops_allocate_pending` should allocate "collections with no settlements yet." I read that as "not yet fully accounted for" rather than a literal zero-settlement-rows count, so a collection that arrived before its plan's cadence was locked (and so had no instalments to allocate against at the time) gets picked up again once `tops_build_plan_instalments` later creates capacity for it — under the strictly literal reading it would not be, since it already has a settlement row. Recorded here so this can be overridden if the narrower reading was intended.

**Cron jobs added:** `tops-allocate-pending-collections-every-10min`, schedule `*/10 * * * *`, command `SELECT public.tops_allocate_pending(2000);`. No existing job touched.

## 2026-09-26 — `20260926190000_tops_plan_position_and_schedule_ledger.sql`

**Objects added** (both pure reads — no `INSERT`/`UPDATE`/`DELETE` anywhere in this file):

- `public.tops_plan_position(uuid, date DEFAULT NULL) RETURNS TABLE(...)` — one row: `rent_request_id, cadence, cadence_source, clock_start, clock_source, term_end_date, expected_to_date_ugx, paid_to_date_ugx, position_ugx, periods_due, days_past_due, days_behind, days_ahead, outstanding_ugx, catch_up_daily_ugx, term_expired, as_at, basis`. `p_as_at` defaults to today's Kampala date. Every money figure (`paid_to_date_ugx`, and everything derived from it: `position_ugx`, `outstanding_ugx`, `catch_up_daily_ugx`) is bounded by the underlying `agent_collections.created_at` (Kampala date) being on or before `as_at`, so a historical `as_at` is a genuine point-in-time snapshot, not today's totals filtered by due date alone. `term_end_date = clock_start + duration_days - 1`, matching the platform-wide convention FINDINGS §1 documents for `v_rent_plan_schedule.term_end`. Cadence `unknown` returns `clock_start`/`clock_source` (those are resolved independently of cadence) but every schedule-derived field null, so the UI states "unknown" plainly rather than showing a fabricated number.
- `public.tops_plan_schedule_ledger(uuid) RETURNS TABLE(...)` — one row per instalment: `seq, due_date, amount_ugx, settled_ugx, outstanding_ugx, running_arrears_ugx, settled_by, never_billed`. `running_arrears_ugx` is a running total that floors at zero at every step (real arrears can't go negative — "ahead" is what `tops_plan_position.position_ugx`/`days_ahead` already represents), which needed a loop rather than a window `SUM`. `settled_by` is a `jsonb` array of `{collection_id, date, channel}` per active (non-released) settlement, oldest first. `never_billed` is true when the instalment's `due_date` precedes `MIN(agent_expected_day_plans.day)` for that plan; when that plan has no pinned day at all yet, it resolves to `false` (a conservative default — see the interpretation note below) rather than asserting every instalment is never-billed.

Both: `SECURITY DEFINER` with an **internal `has_role` check** (`tenant_ops`/`operations`/`coo`/`cfo`/`ceo`/`super_admin`) that `RAISE EXCEPTION`s for anyone else — unlike the internal-engine functions built so far, these are meant to be called by the frontend, so `REVOKE ALL ... FROM PUBLIC, anon` + `GRANT EXECUTE ... TO authenticated` (the has_role check, not the grant, is what actually gates a useful result).

**Interpretation flagged, not silently assumed:**
- `catch_up_daily_ugx`'s exact formula wasn't specified beyond its name and its null-on-expiry rule. Implemented as `outstanding_ugx` spread evenly (rounded up) across the days remaining in the term including today (`CEIL(outstanding / (term_end_date - as_at + 1))`) — "pay this much per day for the rest of your term and you clear the whole balance exactly on time." A different intended meaning (e.g. only the deficit, not the whole outstanding balance) would change this function; flagged here so it can be corrected if intended differently.
- `never_billed` when a plan has never had ANY day pinned in `agent_expected_day_plans` (`MIN(day)` is null): resolved to `false` for every instalment rather than `true`, since "precedes the first pinned bill" is a comparison against something that doesn't exist yet. The opposite reading (treat everything as never-billed when nothing has ever been pinned) is equally defensible; recorded here in case the narrower reading was intended.
