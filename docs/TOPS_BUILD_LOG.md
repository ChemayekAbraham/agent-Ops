Root cause is a pre-existing, schema-wide `ALTER DEFAULT PRIVILEGES ... FOR ROLE postgres IN SCHEMA public GRANT ALL ON TABLES TO authenticated, service_role, ...` entry in `pg_default_acl` (confirmed present before this migration ran, and not something a `CREATE TABLE ... ## 2026-09-26 — `20260926170000_tops_plan_clock_resolver_functions.sql`

**Objects added:**

- `public.tops_resolve_plan_clock(uuid) RETURNS void` — upserts one `tops_plan_clock` row from `rent_requests` + `landlord_payouts`. `clock_start`/`clock_source`: `MIN(landlord_payouts.otp_verified_at)` for that plan (Kampala date) when present → `landlord_receipt`; else `COALESCE(funded_at, disbursed_at, created_at)` (Kampala date) → `funded_at`. Deliberately never reads or writes `rent_requests.repayment_starts_on`. `cadence`/`cadence_source`: `explicit`/(`daily`|`weekly`) only when `repayment_frequency_locked = true` AND `repayment_frequency IN ('daily','weekly')`; everything else (unlocked, or locked `monthly`) resolves to `unknown`/`unknown` — deliberately conservative, matching FINDINGS §3's warning not to copy the existing weekly-shape heuristic. A row already at `clock_source = 'override'` is left untouched (checked before computing, and re-guarded in the `ON CONFLICT ... WHERE` clause).
- `public.tops_build_plan_instalments(uuid) RETURNS integer` — regenerates `tops_plan_instalments` for one plan from its `tops_plan_clock` row. `daily`: one row per day, `clock_start+1..clock_start+duration_days`, amount = `daily_repayment`, last absorbs the remainder to hit `total_repayment` exactly. `weekly`: one row every 7 days, `ceil(duration_days/7)` rows, amount = `daily_repayment*7`, same remainder-absorbing last row. Returns 0 and writes nothing when cadence is `unknown`. Upserts by `(rent_request_id, seq)` so seq stays stable across reruns; only trims a trailing row from a previously-longer schedule when that row carries no `tops_instalment_settlements` row, so a rerun can never orphan settlement history.
- `public.tops_build_schedules_batch(integer DEFAULT 500) RETURNS integer` — the cron entry point. Scans `rent_requests` with `status IN ('funded','repaying')` that have no `tops_plan_clock` row yet, no `tops_plan_instalments` rows yet, or whose `updated_at` is newer than their `tops_plan_clock.updated_at`; calls the two functions above for up to `p_limit` of them, oldest-changed first.

All three: `SET search_path = public`, `SECURITY DEFINER` (owned by the same role as the `tops_*` tables, so they can write despite RLS), and — this matters — `REVOKE ALL ... FROM PUBLIC, anon, authenticated` explicitly naming `anon`/`authenticated`, not just `PUBLIC`. No EXECUTE grant to any client-facing role; these are internal-engine functions only reachable via the cron job.

**Cron jobs added:** `tops-build-plan-schedules-every-30min`, schedule `*/30 * * * *`, command `SELECT public.tops_build_schedules_batch(500);`. No existing job touched.

## 2026-09-26 — `20260926180000_tops_collection_allocation_functions.sql`

**Objects added:**

- `public.tops_is_collection_reversed(uuid) RETURNS boolean` — `agent_collections.reversed_at IS NOT NULL`, per FINDINGS §5's documented rule (deliberately not the `notes` text-marker check `rent_apply_collections_to_days()` uses, which FINDINGS measured as missing 48 reversed collections). - `public.tops_allocate_collection(uuid) RETURNS integer` — allocates one `agent_collections` row across its plan's `tops_plan_instalments`, oldest `due_date` first, `take = LEAST(remaining, instalment_outstanding)`. Recomputes from scratch on every call: excludes the collection's own existing rows when computing each instalment's outstanding room (so it never double-subtracts its own prior contribution), upserts by `(instalment_id, collection_id)`, then deletes any of its own rows the fresh computation no longer touches. A reversed collection releases (`released_at = now()`) instead of allocating, and never allocates once reversed. Returns 0 for a collection with no `rent_request_id`.
- `public.tops_allocate_pending(integer DEFAULT 2000) RETURNS integer` — the cron entry point. Candidate set: any non-reversed collection whose unreleased settlement total is still less than its own `amount` (this includes, but is not limited to, a collection with zero settlement rows — see the interpretation note below), plus any reversed collection that still has an unreleased settlement to release. Processes oldest `created_at` first.

All three: `SET search_path = public`, `SECURITY DEFINER`, `REVOKE ALL ... FROM PUBLIC, anon, authenticated` (the explicit anon/authenticated revoke, per the fix recorded in the previous entry). None of the three writes to `agent_collections`, `general_ledger`, or any wallet table, and none adds a trigger to any of them — confirmed by inspection of the migration's own SQL (the only `INSERT`/`UPDATE`/`DELETE` targets in it are `tops_instalment_settlements`).

I read that as "not yet fully accounted for" rather than a literal zero-settlement-rows count, so a collection that arrived before its plan's cadence was locked (and so had no instalments to allocate against at the time) gets picked up again once `tops_build_plan_instalments` later creates capacity for it — under the strictly literal reading it would not be, since it already has a settlement row. Our own work-item layer — a single ranked queue of "what needs a human's attention right now," built entirely on top of `tops_plan_position` and the same `tops_arrears_ageing` bucket ladder (`new` 1–7 days, `watch` 8–14, `at_risk` 15–30, `critical` 30+ or expired-term-override) already established for one consistent mental model across the workspace. Does not touch `ops_inbox_state` or anything the existing inbox uses — confirmed by inspection, nothing in either migration references it.

**Objects added:**

- `public.tops_work_items` — one row per plan currently needing attention: `bucket`, `reason`, `value_at_risk_ugx`, `assigned_to`/`assigned_at`, `sla_due_at`, `status` (`open`/`in_progress`/`closed`), `closed_outcome`/`closed_by`/`closed_at`, `escalated_to`/`escalated_at`/`escalation_note`. Indexes on `(assigned_to, status)` and `(bucket, value_at_risk_ugx DESC)`. RLS: one SELECT policy for the six `tops_` roles; **no INSERT/UPDATE/DELETE grant or policy at all** — every mutation goes through a named function below. `REVOKE ALL ... FROM PUBLIC, anon` (explicit `anon`, per the standing default-ACL finding).
- `public.tops_notifications` — our own in-app notification feed (`user_id`, `title`, `body`, `work_item_id` FK, `read_at`). The existing `public.notifications` table's insert trigger allows only 8 fixed `type` values (none ours, per `docs/TOPS_FINDINGS.md` §8), so this is a separate, parallel table, not a workaround on the existing one — the existing table/trigger is never touched. RLS: SELECT own-or-ops-role, UPDATE own-only (mark read); no INSERT policy — insert-only via the mutation functions.
- `public.tops_refresh_work_items() RETURNS integer` — the internal engine. Scans `funded`/`repaying` plans with a locked cadence, computes bucket/value-at-risk/reason from `tops_plan_position`, and either updates the one existing open/in_progress item for a plan or inserts a new one — never both, never duplicates an open item for a plan. Never touches `assigned_to`/`status`/`closed_*`/`escalated_*` on an existing item (human-owned fields). SLA defaults by bucket (4h/24h/48h/72h) are this migration's own policy choice — nothing else specified one. Internal-only, no EXECUTE grant to any client role. **New cron job: `tops-refresh-work-items-hourly`, `0 * * * *`.**
- `public.tops_assign_work_item(work_item_id, assigned_to)` — rejects null `assigned_to`, not-found, or already-`closed`; sets `in_progress` + writes a `tops_notifications` row for the assignee.
- `public.tops_close_work_item(work_item_id, outcome)` — **outcome required**, rejected if null/blank; sets `closed`/`closed_by`/`closed_at`.
- `public.tops_escalate_work_item(work_item_id, escalated_to, note DEFAULT NULL)` — **escalated_to required** (an escalation names a person); writes a `tops_notifications` row for them.

**A real, serious bug found by actually invoking the cron path — not by the migration applying:** `tops_refresh_work_items()` called `tops_plan_position()` directly, and `tops_plan_position()` is gated by `has_role(auth.uid(), ...)`. `pg_cron` jobs run with no session and no JWT claim, so `auth.uid()` is `NULL` there — meaning **the hourly refresh cron could never have completed a single run in production**; it would fail `not authorized` on the very first plan it looked at, every hour, silently. This was only caught because the verification step called `tops_refresh_work_items()` a second time with zero impersonation (deliberately mimicking exactly how cron invokes it, rather than only testing inside an impersonated transaction as the rest of the lifecycle test did) and got the same `not authorized` error a real cron run would get.

Fixed with a second migration (`20260927161000_tops_plan_position_internal_for_cron.sql`), same day: extracted `tops_plan_position`'s existing logic into a new `tops_plan_position_internal(uuid, date)` — identical computation, no `has_role` gate, no client EXECUTE grant, internal-only — and made `tops_plan_position()` itself a thin role-gated wrapper around it, so every existing client caller (`PositionCard`, `usePlanPosition`, `CallingSection`, etc.) keeps the exact same signature, gate, and return values. `tops_refresh_work_items()` now calls the internal variant. This is a `CREATE OR REPLACE` on `tops_plan_position` — an existing `tops_` object from an earlier task, not a Classic/non-`tops_` one, so permitted under the additive-only rule; nothing non-`tops_` was touched.

**A second real bug, also found only by invoking the function, not by the migration applying:** `tops_queue_latency` used `ROUND(double precision, integer)`, which does not exist in Postgres — `ROUND` with a precision argument only works on `numeric`. Every call to it errored. Fixed in place (`CREATE OR REPLACE` on our own new function, same task) by casting the `PERCENTILE_CONT` result to `numeric` before rounding; re-verified live afterward, returning `{null, null, 0, 0}` correctly for a window with no assigned/closed items yet.
