# 247. Anonymous access revoked on four sensitive views (2026-10-17)

**Found by:** Supabase advisor on the new project (own account): "Exposed Auth Users" for `v_accounts_no_verified_phone` and "Security Definer View" for `v_user_wallet_strict`, `v_merchant_float_position`, `v_lc1_verification_inbox`.

**Cause:** the views are owned by `postgres` with no `security_invoker`, so they read their tables with the owner's rights (row-level security does not apply), and the default grants gave `anon` (not signed in) and `authenticated` full access. 77 views in `public` have this setup; whether it pre-dates the move cannot be checked (old project disconnected), the grants were restored as dumped.

**Proof before the fix** (count-only requests to the public REST API with the site's public key, no data read): `v_accounts_no_verified_phone` 96,957 rows readable, `v_lc1_verification_inbox` 24,560 rows readable; the two wallet views were permitted but returned HTTP 500 (a failure, not a denial).

**Fix applied to production 2026-10-17:** `revoke all ... from anon` on the four views (migration `20261017100000_revoke_anon_on_sensitive_views.sql`). Verified: `has_table_privilege('anon', ...)` false for all privileges; the same API requests now return 401.

**Not done (decision needed):**
- `authenticated` can still read all four, meaning any signed-in user can read company-wide rows. Fix is either `security_invoker = true` plus a role check, or serving the staff dashboards (`MerchantFloatTruthPanel`, `Lc1VerificationInboxPanel`, `ManagerBankingLedger`, `MerchantFloatRequestsPanel`, `useLandlordOpsToday`, ...) through role-checked functions. `v_user_wallet_strict` is read by 7 edge functions (approve-withdrawal, approve-deposit, cfo-direct-credit, finops-wallet-move, admin float moves): money logic, test before changing.
- Audit the other 73 public views for personal or money data readable by `anon` (some may be public on purpose).

## Step 2a (APPLIED 2026-10-17): landlords_directory + search_landlords_fuzzy
**Found:** `landlords_directory` is an owner-rights view over `landlords` (`security_invoker=off`, apparently by design: a window wider than the table's own row security). Any signed-in user (supporters, tenants) could read all 46,743 landlords with phone, GPS, meter numbers and caretaker phone. Its search RPC `search_landlords_fuzzy` (security definer, reads the view) was **executable by PUBLIC/anon**: a signed-out visitor got landlord names, phones and GPS (verified with a 5-row count-only call). The pasted generic advice (`security_invoker=true`) was NOT applied: it would have blanked the borrower residence checks (`BorrowerResidenceGate`, `BorrowLoanSheet` read the landlord linked on `profiles.borrower_landlord_id`, which the table's row security does not cover), the edit-listing lookup, and shrunk the agent rental finder.
**Decisions (Josh):** row-filter fix; agents keep browsing all landlords.
**Applied** (migration `20261017130000_landlords_directory_row_filter_and_search_guard.sql`): (1) execute on the search revoked from PUBLIC/anon (signed-out call now 401); (2) the view filters rows to the service role / holders of any role other than tenant, landlord, supporter / the user's own landlord (registrant, managing agent, tenant, linked borrower); (3) the search reads `landlords` directly so tenants and borrowers can still find THEIR landlord, but non-agent, non-staff callers need 3+ characters and get at most 10 rows.
**Tested** (probe as each user; before to after): supporter 46,743 to 0 view rows, search needs 3 chars (10 rows max); tenant same; agent and CFO unchanged (46,743; search 100/100/32); borrower with a linked landlord exactly 1 row. **Not covered:** meter numbers and caretaker phone are still visible to every agent through the rental finder (product decision). A tenant, landlord or supporter can still search by name with 3+ characters (needed to link their landlord): harvesting by repeated searches is slower, not impossible; rate limiting is the next step.
**Lesson for the rest of step 2:** the callers of a sensitive view include SECURITY DEFINER functions and RPCs executable by `anon`; check `has_function_privilege('anon', ...)` on every function that reads one. More of these likely exist (3,133 functions in `public`).

## Step 3 (AUDIT, 2026-10-17, read-only; nothing changed, no function was called): owner-rights functions callable by signed-out visitors
`public` has 3,133 functions; **2,796 are SECURITY DEFINER (run as postgres) and 2,795 of them are executable by `anon` (and `authenticated`)** because functions are callable by PUBLIC by default. Excluding 440 trigger functions, **2,355 are callable from outside**. By a source heuristic (does the body call auth.uid()/auth.role()/has_role()/a permission helper at all):
- 1,377 contain some caller check (not proof it is sufficient).
- **978 contain no caller check at all: 292 change data, 392 read sensitive tables (profiles, ledger, wallets, withdrawals, landlords, auth.users, ...), 294 other.**
The 287 distinct no-check writers include money, account and admin functions. Top-of-body source read for five confirmed no check on the caller: `set_staff_access_password(p_user_id, p_new_password)` (upserts any staff user's access-password hash), `credit_agent_tid_backed_float(p_agent_id, p_delta)` (changes any agent's TID-backed float), `create_ledger_transaction(...)` (sets `ledger.authorized = true` itself, then posts), `apply_wallet_movement(...)`, `admin_purge_user_dependencies(p_user_id)` (only refuses accounts with financial history). Others on the same list by name: `record_double_entry`, `deduct_agent_float_for_payout`, `refund_agent_float_for_payout`, `credit_agent_event_bonus`, `credit_merchant_payout_commission`, `record_rent_payment`, `consume_merchant_float`, `auto_dispatch_withdrawals`, `drain_withdrawable_buckets`, `reset_staff_access_password`, `admin_restore_auth_user`, `post_rent_fee_collection`, `rebuild_wallet_projection`. Confirmed for those inspected: owner postgres, security definer, `has_function_privilege` true for BOTH anon and authenticated.
**Not proven:** that any of them can be abused end to end. A function may be protected deeper (a check in a helper it calls, a constraint, a trigger), and I did not execute any. Treat as "reachable with no visible check" until each is tested in a safe environment.
**Complications:** the browser itself calls some of the dangerous ones (`set_staff_access_password`, `verify_staff_access_password`, `reset_staff_access_password`, `create_ledger_transaction`, `record_rent_payment`, `refund_agent_float_for_payout`, `credit_agent_event_bonus`, `validate_and_record_collection` are in the frontend `.rpc()` list), so they cannot simply be revoked; they need an in-function caller check. Cron and other definer functions run as the owner and are not affected by revoking EXECUTE from anon/authenticated; edge functions use the service role.
**Proposed containment (needs Josh's decision):** (1) revoke EXECUTE from PUBLIC/anon/authenticated on every function the browser never calls (service role, cron, definer-to-definer calls keep working), using the full frontend `.rpc()` list; (2) revoke from anon on everything except an explicit pre-login allowlist (sign-in, signup, OTP, short links, invites, fraud/archive checks, public trust/house pages); (3) add an in-function caller check to the no-check functions the browser does call; (4) test sign-in, signup, OTP, public pages and one flow per role before and after; (5) change the default so new functions are not PUBLIC-executable.

## Step 4 (APPLIED 2026-10-18): staff access-password functions and the public manager list
**Found (source read, nothing executed):** `set_staff_access_password(user, new_password)`, `reset_staff_access_password(user, reset_by)` and `verify_staff_access_password(user, password)` had no check on the caller and were executable by anon and authenticated. Anyone could set any staff user's access password, reset it to the default `WelileManager` with a forged audit row (`p_reset_by` was trusted), or guess without limit; and for staff with no password row (all but 11 of the staff) the default password is accepted. Impact is bounded: `/manager-login` is a UI gate (`proceedToDashboard` sets local flags and navigates; real access is still the signed-in session plus RLS), but it was an integrity and audit hole. Also found: `get_manager_profiles()` (the public `/manager-login` list) returned all 17 managers' name, email, phone and photo to signed-out visitors.
**Fix** (migration `20261018090000_staff_access_password_caller_checks.sql`, applied in five small calls because one large call failed with a tool error): `set` needs a signed-in staff role and either own password, an admin role (manager/super_admin/access_admin/ceo/coo/cfo/cto/admin/hr), or a first-login target (no row or must_change); `reset` needs an admin role and `p_reset_by` must equal the caller; `verify` stays callable signed-out but locks a target for 15 minutes after 5 wrong tries (`staff_access_attempts`, no direct access); anon execute revoked on set and reset; `get_manager_profiles` returns email/phone only to signed-in staff.
**Tested as real users with every case rolled back** (11 password rows, 0 attempts, 0 new audit rows afterwards): supporter set denied ("staff only"); supporter reset denied; CFO reset with own id allowed; CFO reset with a forged `p_reset_by` denied; manager sets own allowed; staff without a row sets own allowed; supporter sets own denied; 6th wrong guess returns locked. Manager list: anon 17 rows, 0 emails, 0 phones; supporter same; CFO and manager 17 rows with email and phone.
**Not fixed (product decision):** staff without a password row still accept the default `WelileManager` on first login. Either give each staff member a real password or require a signed-in session for the portal. `/manager-login` also remains reachable signed out. **Watch:** the frontend was not changed; if the portal shows a lock message or a first-login set fails for a manager, the lockout (5 tries/15 min) or the first-login rule is the reason.

## Step 6 (APPLIED 2026-10-18): `record_rent_payment` and `refund_agent_float_for_payout`
**`record_rent_payment(landlord, amount)`** (called by `PayLandlordDialog` after the real money move in the `wallet-transfer` edge function): reduces `landlords.rent_balance_due`. The table guard trigger reverts that column for signed-in callers who are not agents or staff, but it returns early when `auth.uid()` is null, so a **signed-out** caller could clear any landlord's balance. Now: service role, `is_sensitive_field_editor` staff, an agent/senior agent linked to the landlord (registrant, managing agent or active assignment), or the landlord's tenant; anon revoked; amount must be positive. Exposure was small in money terms (37 landlords owe 7,020,631 UGX in total), and the proper follow-up is to do this bookkeeping inside `wallet-transfer` and drop the browser call.
**`refund_agent_float_for_payout(payout, reason)`** (called by the Financial Ops queue "Reject" and by the `landlord-payout-sla-monitor` edge function): restores the agent's landlord float, reopens the allocation and marks the payout failed. The float is deducted by trigger `deduct_float_on_withdrawal` when the payout is created, so a refund is only right **before the landlord is paid**. The old body refused only `completed`, so any caller could refund payouts in `awaiting_agent_receipt` (Financial Ops disburse sets that status: the landlord has been paid) and get the float back: **925 such payouts, 537,655,000 UGX** were refundable by anyone. Now: service role or finance staff only (manager/super_admin/ceo/coo/cfo/financial_ops/admin, or an active staff permission for financial-ops/company-ops), and only while the payout is `otp_verified`, `pending_finops_disbursement`, `pending_merchant_payout` or `disbursing` (the SLA monitor only uses `otp_verified` and `disbursing`); `awaiting_agent_receipt` and `completed` are refused; `failed`/`refunded`/`escalated` stay a no-op. Anon revoked.
**Bug found and fixed while testing (not a security issue):** `agent_landlord_float_allocations.remaining_amount` is a GENERATED column (`greatest(allocated_amount - paid_out_amount, 0)`), but the old function assigned it, so for any payout with an allocation (920 of 925 pending ones) it raised "column remaining_amount can only be updated to DEFAULT". Financial Ops "Reject and refund" therefore always failed for those payouts (121 failed payouts, only 1 with an allocation). The assignment is gone; `paid_out_amount` and `status` still reopen the allocation.
**Tested as real users, all rolled back (925 awaiting payouts, test payout float 0, landlord balance 60,000 unchanged afterwards):** supporter and a plain unlinked agent denied; the plain agent who registered the landlord allowed; CFO reduces a balance 60,000 to 59,000; supporter and the payout's own agent cannot refund; CFO cannot refund a paid payout; CFO refund of a failed payout is a no-op; CFO refund of an unpaid payout (simulated by setting pending inside the test) gives float 0 to 200,000, total_paid_out 3,370,000 to 3,170,000, allocation paid out 200,000 to 0 and remaining 0 to 200,000, payout failed.
Migration `20261018110000_record_rent_payment_and_float_refund_caller_checks.sql`. **Open here:** whether staff should ever refund an already-paid payout (e.g. the landlord was not actually paid, `report_payout_not_received`); today it is refused for everyone but would need an explicit, audited path.
